# Decisions D-421–D-430

> [Decision register index](index.md)

### D-421 — Telegram MVP is one bound private delivery inbox

- One Source accepts direct private messages sent to one configured bot by exactly one numeric `bound_user_id`。The bot does
  not join、observe or synchronize the conversations from which content is forwarded。
- Pairing、first-sender binding、username admission、groups、channels、history import and edited-message lifecycle are outside
  MVP。Source creation uses the existing schema-driven configuration surface。
- One bot identity per Source is deployment guidance，not a cross-Source runtime constraint。
- **Confidence**: explicitly accepted by Sir。

### D-422 — Collection preserves retrieval value rather than Telegram envelopes

- New collection emits existing `core.text.v1` / `core.html.v1` semantic Blocks directly and introduces no Telegram Message
  root。Sender、chat、forward and reply envelope fields are discarded after admission、diagnostics and acknowledgement use。
- The published `extensions.telegram.message.v1` Resolver remains a read-only decoder for `0.1.0` Blocks；new collection
  never emits that shape and no migration rewrites historical Blocks。
- **Confidence**: explicitly accepted by Sir。

### D-423 — Telegram attachment metadata and semantic bytes have separate lifecycles

- Every admitted attachment creates one `extensions.telegram.attachment.v1` metadata Block containing its durable remote
  locator and use-relevant filename/type/size/media facts。Caption remains an independent semantic child。
- Materialized bytes occupy at most one existing core semantic `content` child。Ordinary Resolver text/label/solved reads do
  not trigger remote I/O even when callers pass `materialize_missing=True`。
- One explicit Extension command and optional collection policy invoke the same idempotent materialization operation。
- **Confidence**: Sir requested metadata-first behavior and accepted the resulting Acceptance direction。

### D-424 — Attachment download is Source policy and defaults off

- Source config is exactly `bot_token`、positive numeric `bound_user_id` and `download_attachments=false`。There is no
  Extension default、collect-Job override、scheduler parameter or per-media policy in MVP。
- Metadata-only persistence is a complete configured outcome。When enabled，automatic byte materialization is an enrichment
  after primary metadata/cursor commit；its failure does not roll back or replay primary collection。
- **Confidence**: explicitly requested by Sir and derived against Mail/RSS precedent。

### D-425 — Durable acceptance is acknowledged with a check reaction

- After primary graph/cursor commit，complete acceptance adds one ordinary ✅ reaction to the originating message and sends
  no routine `committed` reply。
- Partial、unsupported and retryable-failure outcomes use replies only when qualification is useful。A partial outcome may
  carry ✅ plus a reply explaining unavailable enrichment。
- Reaction/reply failure is bounded Job diagnostic residue and never replays durable primary content。Telegram's native
  media-group reaction correlation to the first non-deleted item is accepted without album buffering。
- **Confidence**: explicitly requested by Sir and reconciled with Telegram's Bot API contract。

### D-426 — Bot-scoped cursor progress is committed per update

- Source state is `bot_id` plus `last_update_id`。The first collect verifies and pins `getMe().id`；later token rotation must
  resolve to the same bot。A legacy cursor without `bot_id` is unusable and requires a new Source。
- Each update is one primary transaction：lock/recheck Source cursor，persist supported semantic/metadata graph and cursor，
  then commit before external acknowledgement。Primary failure does not advance；unauthorized/unsupported input advances
  without graph so it cannot pin later owner content。
- **Confidence**: explicitly accepted after two-run and concurrency pressure。

### D-427 — Polling remains an ordinary user-triggered Source Job

- Collection uses bounded Bot API `getUpdates` pages through `core.source.collect.v1`。The Extension owns no process-lifetime
  poller、webhook lifecycle、Cron or setup-time schedule。
- With no cursor，the first collection starts at the earliest still-unconfirmed update。Telegram retention loss and latency
  remain consequences of the user's manual/Cron schedule，not a Source completeness promise。
- **Confidence**: explicitly accepted by Sir。

### D-428 — Telegram extension changes remain extension-local

- Telegram runtime implementation is confined to `extensions/telegram/**` plus its generated OpenAPI consequence。It adds no
  Core Source/Resolver/Extension framework or migration change。The later repository-wide release-contract scope in D-429 is
  an orthogonal Unit responsibility and does not move Telegram behavior into Core。
- `python-telegram-bot` `22.8` already owns Bot API mechanics；the extension uses its bounded `Bot` context and does not add a
  second adapter/framework or custom HTTP client。
- **Confidence**: implementation-plan probe and peer overlap review confirmed this boundary。

### D-429 — Replace external Changie with one PDM-managed Core-and-Extension release contract

- Replace the external Go Changie CLI/config with Towncrier as a pinned PDM development dependency。Towncrier owns fragments、
  fragment types and changelog rendering；repository release orchestration owns project discovery、artifact scope、bump
  policy、next version、`pyproject.toml` version mutation and delivery checks。
- Core joins every first-party Extension as a release-contract project，while Extension preview/publication remains explicitly
  Extension-only。Historical changelog content is retained rather than reconstructed from migrated fragments。
- This expands the Unit across root dependency/lock、release tooling/automation、Core and Extension changelog/fragment
  surfaces。The peer roster reserves D-421–D-460 for this Unit，but implementation must move off the still-open PR #88 branch into
  an independent feature branch/worktree or wait for #88 to merge before branching。
- **Confidence**: migration direction、PDM ownership and Core inclusion were explicitly selected by Sir；Release PR cadence is
  resolved by D-430，while exact Core artifact scope remains Technical pressure。

### D-430 — Feature changes carry fragments；an independent Release PR owns preparation

- Ordinary feature PRs add project-scoped Towncrier fragments and do not bump versions or render changelogs。After fragments
  merge to protected `main`，one serialized repository-owned controller creates or updates one dedicated Release PR that
  consumes pending fragments、computes independent project bumps and renders prepared changelogs。
- The Release PR has no canonical publication authority and follows the ordinary protected-main merge gate。After it merges，
  the existing main release lane may publish changed Extension versions；Core is part of version/changelog preparation but is
  never included in the Extension publication matrix，and Core deployment identity remains the exact source SHA。
- Organization governance owns protected-main release authority and forbids PR publication，but deliberately delegates exact
  changelog/version mechanics to repositories。This is therefore a core-py release-detail repair aligned with the existing
  `InKCre/ui` Changesets Release PR precedent，not a new organization-wide mandate or shared-Hub edit。
- **Confidence**: independent Release PR preparation was explicitly required by Sir and matches inspected organization
  governance plus the existing UI repository realization。
