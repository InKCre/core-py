# Decisions D-391–D-400

> [Decision register index](index.md)

### D-391 — SinkManager is the explicit application service；SinkBase is one persisted instance's runtime implementation

- **Manager responsibility**: `SinkManager` owns exact type registration/catalog sync，Sink instance CRUD，validated config
  commands，Peer-scoped enable/disable commands，cold startup/shutdown and the peer-local running-instance map。
- **Base responsibility**: a concrete `SinkBase` object binds one persisted Sink instance，owns its typed config access and
  implements `on_start(app)` / `on_close()`。Because one Sink type may have multiple rows，runtime state is instance-bound，
  not stored on the subclass as it is for the one-installed-record-per-Extension model。
- **Explicit commands**: there is no generic `reconcile(sink_id)` controller、database watcher or polling lifecycle。Create
  persists an inert row；enable/disable explicitly change one Peer's intent and start/stop locally when that Peer is targeted；
  `start_enabled(app)` is the cold-start path。
- **Config behavior**: `SinkManager.update_config()` validates through the registered type。For a running instance it delegates
  to `SinkBase.update_config()`；the Manager does not guess that every config change requires stop/restart。
- **Lifecycle interface**: the shared contract is `on_start(app)` / `on_close()`，not a public
  `run(app) -> AsyncContextManager`。A concrete Sink such as MCPSink may internally use an async context manager or
  `AsyncExitStack` to make its own resource cleanup deep and reliable。
- **Persistence ordering**: enable/disable first records the requested Peer intent，then starts/stops the local instance when
  applicable。Runtime failure remains observable and does not trigger a generic compensation transaction that rewrites the
  requested intent。
- **Confidence**: derived from the existing ExtensionManager/ExtensionBase responsibility split and explicitly accepted by
  Sir after correcting the proposed controller-style reconciliation。

### D-392 — One MCPSink runtime owns one deterministic mounted endpoint and one fresh SDK lifecycle

- **Address**: one persisted MCPSink instance is published at `/sinks/{sink_id}/mcp`。The path is derived from persisted
  identity rather than stored in generic Sink columns or transport-specific config。
- **Ownership**: concrete MCPSink owns its MCP server，ASGI sub-application，bearer boundary，retained Mount and SDK session
  manager。SinkManager only awaits the ordinary SinkBase lifecycle and retains the running object。This endpoint is not a
  Peer inbound/capability。
- **Startup / shutdown**: startup creates a fresh SDK server，enters its single-use session-manager context and only then
  publishes the Mount。Shutdown removes that exact Mount before closing the manager and discarding the MCPSink object。A
  later enable constructs a new runtime object rather than attempting to restart the exited SDK manager。
- **Transport**: MVP uses stateless Streamable HTTP with JSON responses。The seven accepted Tools require no client callback
  channel，and the Sink gains no server-side browse/session authority。
- **Configuration**: the long-lived bearer PAT remains MCPSink instance config。It does not reuse Peer JWT，change Core
  readiness or justify an OAuth/token-service subsystem。
- **Confidence**: accepted by Sir after comparison with the official MCP Python SDK's mounted-ASGI and single-use session
  manager lifecycle。

### D-393 — `use-inkcre` is one goal-facing metacognitive Skill，not an MCP Tool manual

- **Purpose**: one Agent Skill helps an Agent notice when information already collected in InKCre may improve the quality
  or efficiency of the productive/creative work currently underway。The Human need not explicitly ask to search a knowledge
  base，recall something or “find” a fact before the Skill is applicable。
- **Mental model**: the Skill conveys the minimum InKCre mental model and philosophy needed for that judgment：information is
  collected into an info-base，organized to improve later use，and retrieved as Blocks / Relations through Resolver-owned
  meaning。This is Agent-facing metacognition，not a second Product authority or an architecture document。
- **Non-contract**: the Skill does not enumerate a preferred recall→open→read→expand→find-path→resolver-method recipe and
  does not teach retrieval-mode mechanics。Tool names，schemas and descriptions own operational discoverability；the Agent
  composes those atomic actions according to its actual context。
- **Shape**: MVP publishes one `use-inkcre` Skill，not one Skill per Tool or modality。
- **Confidence**: explicitly accepted and corrected by Sir after reviewing the initial operational Skill proposal。

### D-394 — ChatGPT connects through Secure MCP Tunnel while MCPSink keeps its ordinary PAT contract

- **Direct MCP contract**: ordinary MCP Hosts call `/sinks/{sink_id}/mcp` with the MCPSink instance's long-lived bearer PAT。
  The PAT remains required；it does not become nullable and MCPSink does not add an anonymous mode。
- **ChatGPT contract**: a customer-run OpenAI `tunnel-client` forwards the same MCP endpoint and injects that PAT as a static
  downstream `Authorization` header。ChatGPT selects the OpenAI-hosted Tunnel through Developer Mode and never needs to
  store or present the custom PAT itself。
- **Ownership**: Secure MCP Tunnel is a ChatGPT-specific operator companion，not application business code，a Sink type，a
  Sink transport abstraction or a second MCP implementation。MCPSink owns the unchanged Tool/Skill endpoint behind it。
- **OAuth**: this unit does not implement MCP OAuth or an Authorization Server。A permanent single-user InKCre deployment
  has no user/account/consent lifecycle whose product value would repay OAuth metadata，client registration，PKCE and token
  lifecycle ownership。
- **Delivery boundary**: Tunnel serves personal/private Developer Mode connections and requires a running `tunnel-client`
  companion。Public Plugin-directory distribution remains outside this unit。
- **Confidence**: explicitly accepted by Sir after verifying current OpenAI Developer Mode，Tunnel static downstream-header
  support and MCP OAuth requirements。

### D-395 — Seven MCP Tools adapt existing domain owners without a second retrieval layer

- **Recall**: `inkcre_recall` delegates each explicit mode to `LexicalRetrievalManager.retrieve()` or
  `SemanticRetrievalManager.retrieve()`。MCPSink owns concurrent composition，entity de-duplication and preservation of
  mode-local evidence；it does not own ranking or retrieval records。
- **Entity/content reads**: `inkcre_open_entities` uses Block/Relation Managers for identity lookup。
  `inkcre_read_blocks` uses Block hydration and Resolver solved-content contracts。MCPSink owns entity-ref parsing，bounded
  previews and MCP adaptation for large/multimodal content。
- **Graph navigation**: `inkcre_expand_entities` and `inkcre_find_path` delegate neighborhood/path semantics to
  `GraphNavigationRetrievalManager`。MCPSink batches/adapts results without adding traversal policy。
- **Dynamic Resolver behavior**: `inkcre_resolver_methods` and `inkcre_invoke_resolver_methods` consume ResolverManager's
  exact registry and ordinary typed Resolver methods。MCPSink owns read-intent projection，on-demand schemas，batch
  execution and MCP result adaptation。
- **Rejected layer**: no `MCPSinkRetrievalManager`，generic Tool dispatcher，or MCP-specific methods on existing domain
  Managers are introduced。
- **Confidence**: explicitly accepted by Sir after mapping all seven stable Tools to inspected current managers and content
  contracts。

### D-396 — `use-inkcre` teaches only the info-base model exposed through this MCP surface

- **Trigger**: the Skill still helps an Agent notice when previously collected information may improve current
  productive/creative work without requiring an explicit retrieval request。
- **Mental-model scope**: the Skill explains only Block，Relation，Resolver and Storage well enough for an Agent to interpret
  and use MCP results correctly。It does not teach Source，collection，organization，sink lifecycle or the full
  collect→organize→use product topology，because this read-only MCP surface cannot operate those domains。
- **Use posture**: retrieved graph/content remains contextual information rather than a generated answer；Tool schemas own
  operational mechanics，and the Skill prescribes neither a fixed Tool sequence nor recall-mode instructions。
- **Ownership**: Hub remains authoritative for the underlying info-base concepts；core-py MCPSink owns the concise
  Agent-facing `SKILL.md` projection and MCP delivery mechanics。
- **Confidence**: explicitly accepted and narrowed by Sir to match the capability actually exposed by the unit。

### D-397 — Block content Resources are deterministic live projections，not persisted entities

- **Independent dimensions**: `raw|hydrated|solved` selects the InKCre content layer；text/JSON/bytes describes the value；
  embedded content versus Resource link is only MCP delivery。MCPSink must not merge these into one mode or substitute one
  content layer for another。
- **Projection identity**: each result has a deterministic URI such as
  `inkcre://blocks/{block_id}/content/{mode}`。`resources/read` resolves that URI lazily from current Block，Storage and
  Resolver authority；the URI is not an immutable version or snapshot。
- **No new authority**: this unit adds no Resource table，download-session model，snapshot store or independent Resource
  cache。Tool-returned Resource links need not be enumerated by `resources/list`。
- **Delivery**: bounded text/JSON is embedded；oversized or non-inlineable payloads use Resource links with MIME/size hints
  when known。Bounded image/audio may use native MCP content blocks only if the real Host path proves that they reach the
  model correctly。The inline budget remains an internal compatibility constant rather than an Agent parameter or product
  config absent contrary acceptance evidence。
- **Result shape**: the structured batch result correlates Block identity with content URI；standard MCP content-block types
  express embedded-versus-linked delivery。No redundant `found`，`inline`，`delivery` or repeated mode discriminator is added。
- **Typed solved values**: MCPSink owns one common lossless projector for JSON-compatible facts plus nested bytes。Resolver
  and Extension implementations gain no MCP-specific result types or adapters；preflight must inspect real result shapes
  before freezing the smallest projector realization。
- **Confidence**: accepted by Sir after distinguishing deferred context inclusion from payload-size reduction and preserving
  existing info-base authority。

### D-398 — Deterministic MCP contract acceptance and probabilistic ChatGPT product observation are separate evidence

- **Protocol/domain authority**: an independent MCP client drives one real mounted endpoint，PAT and info-base corpus through
  the composable seven-Tool surface，including deferred Resource reading and Resolver-specific method invocation。This is the
  deterministic contract evidence。
- **ChatGPT authority**: Developer Mode connects to the same endpoint through Secure MCP Tunnel，imports `use-inkcre` and
  exercises a real productive task where stored information may help without a literal search instruction。This is manual
  product evidence for metacognitive triggering and contextual use。
- **Lifecycle authority**: enable/disable/re-enable proves route withdrawal and fresh SDK runtime creation；Extension disable
  closes active effects without rolling back process-monotonic Resolver type publication。
- **Automation boundary**: probabilistic model Tool selection and Skill triggering are not promoted into stable automated
  pass/fail assertions。Deterministic protocol behavior carries the enforceable contract；ChatGPT behavior remains observed
  evidence。
- **Confidence**: explicitly accepted by Sir。

### D-399 — Resolver method projection requires both read-intent naming and Agent-JSON representability

- **Candidate set**: MCPSink considers only public bound instance methods named `get_*` or `read_*`。This consumes the
  Resolver API's use-neutral intent convention rather than Agent/MCP metadata。
- **Boundary test**: every caller-supplied parameter must have a non-variadic typed signature from which Pydantic can derive
  JSON Schema。A method requiring an application object such as `sqlmodel.Session` is omitted from Agent discovery。
- **Invocation**: only identities produced by this projection may be invoked；the same derived Pydantic model validates raw
  Tool arguments once，then ordinary typed values reach the Resolver。Results use the common MCPSink content projector。
- **No second authority**: no decorator，allowlist，Resolver metadata，dependency-injection surface or secondary capability
  registry is introduced。Omission means only that an ordinary Resolver method cannot cross this Agent transport boundary。
- **Evidence**: current `Resolver.get_existing(db_session)` and GitHub's override prove that prefix-only reflection would
  expose an uncallable producer-reconciliation operation。
- **Confidence**: explicitly accepted by Sir。

### D-400 — Deterministic acceptance uses a dedicated real corpus；ChatGPT observation may use production info-base

- **Deterministic corpus**: protocol/domain acceptance uses a dedicated local or preview corpus created through ordinary
  producer/Manager paths，not mutable personal production state，test-only Resolver methods or implementation branches。
- **Coverage**: the corpus includes bounded text/structured content，storage-backed multimodal content，oversized content，a
  small directed graph with an alternate branch，an Extension-delivered Resolver Block and ordinary lexical/semantic
  maintenance records。
- **Content authority**: use useful real public material，but do not let its subject shape production behavior or add fake
  retrieval rows。
- **Product observation**: the manual ChatGPT journey may use Sir's real production info-base because task relevance and
  metacognitive use—not deterministic protocol behavior—is the evidence there。
- **Confidence**: explicitly accepted by Sir。
