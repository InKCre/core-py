# Decisions D-381–D-390

> [Decision register index](index.md)

### D-381 — MCP consumes the Resolver registry without changing Resolver or Extension ownership

- **Accepted topology**: an Agent discovers Resolver behavior applicable to a Block，invokes selected behavior，MCP adapts
  arguments/results，and the ordinary Resolver implementation executes the domain behavior。
- **Resolver neutrality**: Resolver methods remain use/sink-neutral typed behavior。Resolver and ResolverManager do not own
  Agent-facing names，MCP schemas or MCP registration。
- **Extension neutrality**: Extension only delivers/registers Resolver implementations through the existing lifecycle。It
  does not add a parallel MCP adapter，hook，schema or Agent-facing capability contribution。
- **Dynamic source**: MCP observes the current peer-local ResolverManager registry and derives its available Resolver-use
  surface from that existing runtime truth。It does not create an Extension-parallel capability registry。
- **Open invocation grain**: the sequence wording “invoke one method” is illustrative，not an accepted restriction。Whether
  discovery/invocation is direct，batched，or otherwise composed remains technical design work。
- **Confidence**: Sir accepted the Agent→Resolver architecture and Extension boundary，while explicitly retaining room around
  discover/invoke-one-method semantics。

### D-382 — Resolver method access uses a bounded progressive MCP surface

- **Resolver naming contract**: public Resolver methods use intent-revealing prefixes。`get_*` / `read_*` express
  read/query intent；`create_*` / `update_*` / `delete_*` / `materialize_*` / `recompute_*` express explicit mutation
  intent；internal mechanics are non-public。A read-intent method may still perform contract-owned lazy materialization。
- **Base behavior**: the five accepted deep tools continue to carry general Resolver behavior without duplicate per-method
  Tools：`inkcre_recall`、`inkcre_open_entities`、`inkcre_read_blocks`、`inkcre_expand_entities` and
  `inkcre_find_path`。
- **Specific behavior**: add two bounded Tools，`inkcre_resolver_methods` and `inkcre_invoke_resolver_methods`。The former
  discovers extra read-intent methods applicable to supplied Blocks；the latter invokes selected semantic method-call atoms。
- **Batching**: invocation may carry multiple independent calls as an envelope，preserving per-call identity and allowing
  concurrency without turning the batch into one coarse domain action。
- **Derivation**: MCP derives method description and schema from the exact runtime Resolver's ordinary typed public contract；
  Resolver and Extension add no MCP metadata or second registry。
- **Portability trade-off**: method-specific schemas are discovered at runtime instead of publishing every method as an
  always-visible native MCP Tool。This bounds the catalog and works without assuming Host-specific deferred loading。
- **Confidence**: Sir accepted the naming constraint and the seven-Tool bounded progressive design。

### D-383 — Resolver-method discovery accepts Blocks or exact Resolvers and normalizes redundant input

- **Inputs**: `inkcre_resolver_methods` accepts `blocks` or `resolvers`。When both are present，non-empty `blocks` takes
  precedence instead of producing a mutual-exclusion error；when neither supplies a target，ordinary input validation still
  reports that no operation can be performed。
- **Block discovery**: Blocks are resolved to their exact Resolver and grouped by Resolver。One result therefore carries
  `blocks: int[]` rather than repeating identical method contracts once per Block。
- **Resolver discovery**: exact Resolver IDs may be supplied directly，including IDs learned from `inkcre_open_entities`。
  These results omit `blocks` because no Block target was part of discovery。
- **Invocation**: `inkcre_invoke_resolver_methods` retains the accepted `{block, method, arguments}` call shape；the Block
  remains the authority selecting its exact Resolver at invocation time。
- **Agent-tool principle**: when redundant inputs leave intent unambiguous and normalization has no harmful semantic cost，
  prefer deterministic precedence/defaulting over rejecting the call。This is not permission to hide inputs for which the
  requested operation cannot be determined or performed。
- **Confidence**: Sir specified Block precedence，Resolver-direct discovery and Resolver-grouped results。

### D-384 — Sink domain owns concrete implementations through SinkManager and SinkBase

- **Topology**: `SinkManager + SinkBase -> MCPSink`。`MCPSink` is one concrete peer-local Sink implementation，not the
  domain Manager。
- **Manager owner**: `SinkManager` owns Sink registration and lifecycle；runtime callers depend on this domain owner rather
  than directly on the MCP protocol implementation。
- **Base contract**: `SinkBase` is the extension point implemented by concrete Sinks。The exact minimal lifecycle contract
  remains technical-design work and must not assume every Sink is HTTP or MCP-shaped。
- **Extension direction**: a future Extension may deliver/register another `SinkBase` implementation；it does not mutate
  `MCPSink` or contribute an MCP-specific parallel adapter merely because it is an Extension。
- **Correction**: this supersedes the packet's candidate `MCPSinkManager` topology。Avoiding a generic sink framework did
  not justify skipping the actual Sink domain owner，but the Manager/Base pair also does not authorize speculative Sink
  persistence，configuration or transport abstractions。
- **Confidence**: Sir explicitly corrected the topology to `SinkManager + SinkBase -> MCPSink`。

### D-385 — SinkBase abstracts reversible peer-local publication，not delivery semantics

- **Minimal contract**: a concrete core-py Sink provides one `run(app) -> AsyncContextManager[None]` lifecycle under an
  exact Sink type。Entry publishes/starts the Sink；exit reverses publication and releases owned runtime resources。
- **No false business method**: `SinkBase` does not define `deliver()`。MCP is pull-oriented while future Sinks may be push，
  UI or background integrations；publication lifecycle is the demonstrated commonality，not one invented delivery command。
- **Manager behavior**: `SinkManager` owns exact registration，registry snapshot/restore and ordered lifecycle entry/exit。
  Extension publication can therefore withdraw a contributed Sink without mutating `MCPSink`。
- **MCP realization**: `MCPSink.run()` mounts Streamable HTTP，runs the official SDK session manager and reverses both on
  exit。Its seven Tools and content adaptation remain implementation-owned beneath that lifecycle。
- **Deferred without scaffolding**: no sinks table，Sink instance/config model or generic transport is introduced until a
  concrete second Sink demonstrates the need。
- **Confidence**: Sir accepted this minimal Manager/Base contract。

### D-386 — MCPSink authenticates external consumers with one deployment-scoped long-lived PAT

- **Identity boundary**: an MCP Host/Client is an external Sink consumer，not an InKCre Peer。Peer JWT and its lifecycle are
  therefore not reused merely because core-py serves the endpoint。
- **MVP credential**: `MCPSink` accepts one deployment-scoped long-lived bearer PAT from concrete config key
  `core.sink.mcp` under schema `core.sink.mcp.config.v1`。
- **Persistence**: the PAT remains an ordinary value in the existing deployment-scope `configs` module。No token table，hash，
  scope，user，tenant，rotation or expiry subsystem enters this unit。
- **Runtime behavior**: replacing the configured token invalidates the previous value。Missing configuration makes MCP
  unavailable explicitly without making the rest of core runtime unready。
- **Protocol boundary**: ordinary Authorization middleware protects the mounted MCP ASGI application。The deployment PAT
  does not pretend to be OAuth and does not publish a fictional issuer/discovery flow。
- **Evolution**: if multiple devices，rotation，expiry or richer admission becomes valuable，a centralized key/token service
  may replace this concrete check without changing the Agent tool surface。
- **Confidence**: Sir accepted the PAT and explicitly rejected treating MCP Host/Client as a Peer。

### D-387 — SinkManager manages each registered Sink independently

- **Essential event**: Extension or core registers one exact `SinkBase` implementation；`SinkManager` starts that Sink when
  the Manager is running，or retains it for startup when registration occurs earlier。
- **Independent lifecycle**: each Sink owns an independent `run(app)` context and running handle。Registering，starting，
  stopping or failing one Sink does not create an ordering or dependency relationship with other Sinks。
- **Withdrawal**: unregistering one exact Sink stops and removes that Sink only。The caller that registered it participates in
  its own lifecycle；Sink domain does not inspect Python module/distribution unloading to infer ownership。
- **Manager state**: the minimal useful state is an exact registered-Sink map plus an exact running-context map。There is no
  batch publication diff，global transaction or reverse-order cross-Sink teardown contract。
- **Correction**: supersede D-385's implication that Extension registry snapshot/restore is the primary Sink lifecycle model。
  Current Extension loader mechanics are downstream integration details，not Sink-domain concepts。
- **Confidence**: Sir identified the independent registration/start model and rejected the module/publication-driven design。

### D-388 — Sink type registration、Sink instance persistence and Sink runtime are separate lifecycles

- **Type registration**: core or an enabled Extension imports a concrete `SinkBase` subclass and registers only its exact
  Sink type/code capability。Registration does not create a Sink instance and does not start it。
- **Persistent instance**: `sink_types` is the runtime-reconciled type catalog；`sinks` owns configured Sink instances，their
  config and enablement intent。Concrete column shape and Peer scope remain the next technical-design question。
- **Runtime selection**: `SinkManager` constructs and runs only persisted Sink instances whose type is registered and whose
  enablement selects the current Peer。A registered Sink type is inert by default。
- **Extension boundary**: an Extension contributes Sink types during `on_start` in the same sense that it contributes Source
  types and Resolvers。Extension enablement makes code capability available；it does not own the configured Sink instance's
  enable/run command semantics。
- **No invented lifecycle API**: the Sink domain does not introduce a public `unregister()` command，registration-triggered
  start，registered/running context maps，or Sink-owned snapshot/diff/restore model。Existing Extension publication rollback
  for Source/Resolver is loader compensation and must not be mistaken for the ordinary Sink lifecycle。
- **Correction**: this supersedes D-385's “no sinks table” decision and D-387's registration-triggered runtime model。The
  useful commonality with Source/Storage is type registry + persisted instance，not one process-local context per class。
- **Confidence**: direct inspection of `SourceManager`、`StorageManager`、`ResolverManager` and Extension publication，plus
  Sir's correction of the intended Sink management model。

### D-389 — Extension active runtime is reversible；registered Python capability types are process-monotonic

- **Process contract**: one process loads at most one exact version of an Extension。Changing that version requires process
  restart；the runtime does not simulate a Python hot upgrade by deleting packages from `sys.modules`。
- **Monotonic registration**: Source、Resolver、Storage and Sink type registrations remain available for the process lifetime
  after successful import。Extension disable does not snapshot、diff or restore those domain registries。
- **Hot-disable boundary**: disable still removes/stops truly active Extension-owned effects：HTTP routes、Peer inbounds，
  connections、background work and other resources explicitly released by `on_close()`。It does not revoke passive type
  definitions already delivered to their owning domains。
- **Failure trade-off**: a failed startup may leave an inert imported type registered。Without a persisted instance or active
  route this does not start behavior，and process restart remains the clean recovery。That bounded residue does not justify a
  cross-Manager pseudo-transaction。
- **Required correction**: remove Source/Resolver registry rollback from Extension publication and remove simulated package
  unloading/restoration；narrow publication bookkeeping to active effects that actually require teardown。Do not reproduce
  the rejected machinery for Sink types。
- **Unit scope**: this correction is implemented inside `mcp-sink` because the new Sink lifecycle exposed the invalid shared
  premise and implementing Sink against it would compound the debt。
- **Confidence**: Sir accepted the ROI analysis and explicitly required correction in this unit。

### D-390 — Sink enablement is persisted per Peer and defaults to disabled

- **Enablement**: one `sinks` row carries `enabled: PeerRef[]`，matching the deployment's peer-local execution reality。An
  empty list means the configured Sink instance is inert everywhere。
- **Runtime selection**: a Peer runs an instance only when its own ref is present and the instance's exact Sink type is
  registered in that process。Registration alone never changes `enabled`。
- **Configuration owner**: concrete instance config—including the MCPSink deployment-scoped bearer PAT—belongs to the
  `sinks` row and is validated by the registered type's config schema。
- **Confidence**: Sir accepted the type/instance/runtime model and the proposed Peer-scoped enablement conclusion。
