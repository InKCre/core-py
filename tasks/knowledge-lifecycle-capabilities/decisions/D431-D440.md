# Decisions D-431–D-440

## D-431 — A Core version change selects normal production and stable delivery

- The root Core project version is the normal production-release selector。An ordinary protected-`main` change whose Core
  version is unchanged may retain CI、immutable source-SHA/digest evidence and a mutable `main` candidate reference，but does
  not normally deploy production or advance `stable`。
- A merged Release PR that changes the Core version selects that exact protected-`main` artifact for production deployment and
  `stable` promotion。A Release PR affecting only Extensions does not deploy Core，and Core never enters the Extension
  publication matrix。
- Core SemVer is the release-selection and Human changelog contract，not the artifact locator。The deployed identity remains
  the exact source SHA/digest，so version governance does not weaken provenance or recovery observability。
- Explicit `workflow_dispatch` remains a visible recovery lane that can redeploy a selected current artifact without creating
  a synthetic version/changelog change。It is not the ordinary unversioned release path and gives no pull request publication
  authority。
- **Confidence**: explicitly accepted by Sir after inspecting the current publish/deploy workflows and their every-`main`
  behavior。

## D-432 — Repository orchestration maps changed surfaces to release projects

- Towncrier does not decide whether a repository change affects Core、one Extension or several projects。It consumes fragments
  already assigned to one project，validates their types and renders that project's changelog。Repository release orchestration
  and CI own monorepo project-impact classification。
- Core impact is a change to delivered Core behavior：`app/**`、`libs/**`、`migrations/**`、`utils/**`、Core bootstrap and
  database/runtime/delivery inputs，or the production dependency projection。An Extension Distribution input maps only to
  that discovered Extension。A mixed change maps to every affected project independently。
- Generated evidence such as `docs/openapi.json` follows the behavior owner that caused it and does not independently make
  Core affected。Towncrier configuration、Release controller/workflow、contributor guidance and development-only dependency
  changes are release infrastructure and do not manufacture a Core Release。
- Root `pyproject.toml` / `pdm.lock` classification compares the production dependency projection rather than raw file bytes，
  so adding or updating the PDM-managed Towncrier development tool does not require an unrelated Core version bump。
- Feature CI requires at least one valid fragment for every affected release project。It rejects both missing project intent
  and version/changelog preparation in a feature PR；the independent Release PR remains the sole preparation owner。
- **Confidence**: Sir confirmed the monorepo project-impact interpretation and the proposed ownership table。

## D-433 — Use project-local Towncrier fragments with native orphan identifiers

- One root `towncrier.toml` owns the shared rendering contract。Core reads fragments from root `.changes/` and writes root
  `CHANGELOG.md`；each discovered Extension reads `extensions/<id>/.changes/` and writes that project's existing
  `CHANGELOG.md`。Repository orchestration invokes the shared config with the selected project directory and explicit version。
- Fragment types are exactly lowercase `added`、`changed`、`deprecated`、`removed`、`fixed` and `security`，rendered under
  the corresponding current changelog headings。They retain the D-429 bump mapping；Towncrier validates and renders the type，
  while release orchestration selects the bump。
- A contributor creates a collision-safe orphan fragment named `+<Towncrier-generated-id>.<type>.md`。An issue or pull-request
  number is optional context rather than a filename prerequisite；the repository adds no custom fragment-ID service or wrapper
  solely to allocate names。
- One fragment communicates one release-project change useful to that project's users。Implementation-only detail and pure
  release-infrastructure work do not create misleading project news。Release preparation consumes the selected project
  fragments and includes their deletions in the Release PR。
- Existing Extension changelog history remains below a Towncrier cutover marker without reconstructing historical fragments。
  Core receives a new changelog boundary at its current baseline，but the migration does not invent pre-existing Core release
  history。
- **Confidence**: explicitly accepted by Sir after comparison with Towncrier's native monorepo、Markdown and orphan-fragment
  contracts。

## D-434 — Keep the Release PR controller as one regenerating workflow

- After a successful protected-`main` repository check，one workflow prepares all pending projects from that checked main SHA。
  Repository concurrency uses `cancel-in-progress` so the latest main-derived run replaces earlier work。
- With no generated release diff，the workflow exits。Otherwise it force-updates one generated `release/next` branch and
  creates the Release PR only when no open PR already targets that branch；later runs update the same PR through the same branch。
- The generated branch is disposable output，not a Human editing surface。Ordinary edits belong in feature fragments and the
  next controller run may replace branch contents without a lease、commit-attestation or branch-ownership protocol。
- The controller uses repository `GITHUB_TOKEN` plus ordinary `git` and `gh`。It adds no PAT、GitHub App、third-party PR action、
  extra dispatch path or speculative stale-run state machine。The Release PR relies on the repository's normal review and
  required checks。
- Towncrier still renders under a no-Git temporary directory because its confirmed native `git add` / `git rm` behavior would
  otherwise mutate the caller's index。That isolation addresses a demonstrated tool side effect，not an external security
  boundary。
- **Confidence**: the independent Release PR behavior was previously accepted；Sir explicitly requested removal of the
  over-designed safety boundary and accepted this minimum controller。

## D-435 — Pre-1.0 breaking changes advance minor rather than major

- For a stable project，`removed` or another explicitly breaking change advances major。For a project whose major version is
  zero，the same breaking change advances minor and resets patch；for example，Telegram `0.1.0` becomes `0.2.0` rather than
  claiming stable `1.0.0` maturity。
- The remaining bump policy is unchanged：`added` and `deprecated` select minor，while `changed`、`fixed` and `security` select
  patch。Multiple fragments still select the highest applicable bump for that project's current maturity line。
- The repository release orchestration owns this maturity-aware calculation；Towncrier continues to own type validation and
  changelog rendering without becoming a SemVer policy engine。
- **Confidence**: explicitly accepted by Sir after the conflict between Telegram's previously accepted `0.2.0` target and the
  unconditional `removed -> major` rule was exposed。

## D-436 — Publish the lifecycle as optional organization release guidance

- `InKCre/.github` may document the feature-fragment -> independent Release PR -> protected-main delivery lifecycle as
  tool-agnostic guidance/reference/example。It does not make Towncrier、one branch name、one bump implementation or core-py
  project mapping an organization-wide requirement。
- The organization guidance explains responsibility boundaries：repositories classify affected release projects and calculate
  versions；a fragment tool validates/renders project news；a Release PR prepares but does not publish；protected `main` retains
  canonical delivery authority。It includes the pre-1.0 breaking-to-minor convention as recommended SemVer guidance。
- Placement is one small `.github/RELEASING.md` durable reference linked from the protected-main release section of
  `.github/GOVERNANCE.md`。Repository-local documentation remains the owner of exact commands、paths、checks and automation。
- The currently checked-out `.github` branch belongs to unrelated `feat/thin-github-workflows` work。This Unit must edit an
  independent `.github` worktree/branch from current `origin/main` and must not mix or commit that other task's state。
- **Confidence**: Sir explicitly authorized an organization guidance/reference/example update while retaining repository-local
  implementation authority；placement follows the inspected `.github` ownership model。

## D-437 — Parallel task sessions are peers with no coordinator role

- Every active Unit session has equal task-protocol standing。The program packet、roster、decision register and shared
  architecture/control files are authorities as documents；no session is their standing coordinator or integration owner。
- A peer self-declares its Unit、placement、owned surfaces and an unused decision range in the latest roster before writing。
  It owns its Unit/range and may apply the smallest task-wide navigation/state consequence of its accepted work while
  preserving other peers' rows、ranges and dirty state。
- When surfaces、baselines or task-wide conclusions intersect，the involved peers communicate and serialize directly。Only an
  unresolved material Product、ownership、risk or authorization fork returns to Sir；a relay session is not introduced。
- Existing range allocations and placement facts remain valid。Messages or edits previously made by the former coordinator
  session are ordinary peer evidence/current-state changes，not a continuing role or superior authority。
- **Confidence**: explicitly required by Sir as a correction to the task-packet collaboration mode。

## D-438 — Use Telegram's supported thumbs-up reaction for durable acceptance

- D-425's post-commit native-reaction behavior remains accepted，but its exact `✅` emoji is superseded because Telegram's
  closed ordinary-reaction set does not contain that emoji and the real Bot API returns `Reaction_invalid`。
- Complete durable acceptance uses one ordinary `👍` reaction。This preserves reaction-only success acknowledgement and the
  existing commit-before-notification、diagnostic-only notification-failure semantics without adding a reply or custom-emoji
  mechanism。
- **Confidence**: real private-bot acceptance evidence established the platform constraint；Sir explicitly accepted `👍` as
  the supported replacement。
